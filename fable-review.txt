CRITICAL FINDING -- same failure class as the prior review, recurred
===========================================================================
Dashboard claim (dashboard.html, current): "Woz: 128 CPU Opcodes GREEN +
Klaus Dormann harness." This phrasing is actually more careful than last
time's false "100% passing" claim -- it only claims the harness EXISTS, not
that the suite passes. Good improvement in precision.

BUT: I ran tests/test_functional_suite.c directly (it builds fine, the
fixture tests/fixtures/6502_functional_test.bin is present) and it FAILS:

    FAIL: test_functional_suite_reaches_success_trap
    (trapped at $0FAB after 42450 steps -- expected success trap at $3469)

Root cause, confirmed by reading src/cpu6502.c directly: ADC/SBC do not
implement BCD (decimal mode) arithmetic. The code says so explicitly:

    case 0x69: { /* ADC immediate (binary mode only; decimal mode is a
                    separate future test per NEXT_STEPS.md flag coverage) */

This is a known, bounded, scoped-out gap -- not a mystery bug. But two
problems follow from it:

1. tests/test_functional_suite.c is NOT wired into `make test` (unlike
   test-firmware and test-biosim, which ARE documented as separate targets
   with an explicit comment explaining why they're excluded). This one has
   no such target and no such comment -- it's just silently absent. Anyone
   running `make test` and seeing "159 tests GREEN" has no way to know the
   actual ISA-correctness suite fails.
2. Decimal mode is used by real Apple II software more often than people
   expect -- BASIC's floating-point/string routines and various games'
   scorekeeping lean on it. This will surface as a real bug once actual
   Oregon Trail code runs, not just as an academic test-suite gap.

RECOMMENDATION (hardware in hand next week -- this is the highest-priority
open item): either (a) implement decimal-mode ADC/SBC now -- it's a
well-known, bounded algorithm, not exploratory work, or (b) if deferring,
add an explicit `make test-functional` target (mirroring the existing
test-firmware/test-biosim pattern) so the gap is visible and tracked in CI
language, not silently missing. Right now it is neither passing nor
tracked, which is the worst of both states.

===========================================================================
ARCHITECTURE / SECURITY -- holds up on direct inspection
===========================================================================
- Bus-abstraction contract (read6502/write6502 as the single seam for
  RAM/ROM/soft-switches) remains the right call -- it's what let three
  people's modules (Woz/Bunnie/Duke) develop in parallel against mocks and
  get swapped to the real bus later without cross-module coupling.
- Fast-sector-read disk trap (bypassing GCR/stepper emulation, direct ReRAM
  pointer copy) is a smart, correctly-scoped simplification given the
  actual goal (boot speed, not floppy-drive authenticity).
- Bounds-checking discipline is consistent everywhere I checked: rram_driver
  rejects unaligned/out-of-bounds writes (tested), disk_trap rejects
  invalid track/sector without corrupting state (tested), video decode has
  explicit first/last-column boundary tests (tested). This is real, not
  decorative.
- BRAINSTORM.md updates (Section 7 power numbers, BIO ISA confirmed as
  RV32IMC with reserved x16-x31 MMIO registers) read as incorporating real
  external information (Discord #c-side channel, bunnie huang directly)
  with appropriate epistemic hedging -- commit 9d00f76 explicitly labels
  claims "CONFIRMED-from-photo" vs "ASSUMED," which is the right posture
  for hardware not yet in hand.
- No meaningful new security-surface concerns beyond what was already
  noted last review (no external/untrusted input path reaches the decode
  functions; .dsk contents are baked in at build time, not loaded from an
  untrusted external source at boot).

---------------------------------------------------------------------------
Integration-test gap identified (not yet fixed, real open item)
---------------------------------------------------------------------------
No .dsk file exists anywhere in the repo. cartridge_slots[] is an address
table, not content. The Dormann suite and all 484 unit tests exercise
components in isolation or against synthetic bytes -- none of them boot a
real disk image through the composed system (cpu6502 + apple2_mem +
disk_trap + emulator_loop together). This is the one class of bug unit
tests structurally cannot catch.

Recommended "hello world": a stock DOS 3.3 system master .dsk (boot to `]`
prompt, zero game logic) embedded via tools/embed_disk.py and driven
through the real emulator_loop.c -- not a game, not Oregon Trail yet, pure
disk-controller+CPU+ROM validation of the composed system.

---------------------------------------------------------------------------
Simulator-rig question -- no full-system rig exists, and building a guessed
one is not recommended
---------------------------------------------------------------------------
Three separate simulation tools exist, none of them a system simulator:
1. bio-sim (Verilator RTL sim of real BIO_bdma hardware) -- BIO firmware
   only, external checkout, real silicon behavior.
2. QEMU (qemu-system-riscv32 -M virt) -- used only for bio_audio.S RV32E
   instruction-level checks via a SiFive test-finisher device. Generic RV32
   core, no Baochip-specific memory map or peripherals.
3. Host-native C harness (make test) -- where all real TDD work lives;
   mocked/synthetic buses, not a hardware simulation at all.

Tried running the real build-riscv/baoregon.elf under QEMU virt as a raw
boot smoke test. Result: inconclusive by design, not a pass -- linker.ld
places code at 0x20000000 (Baochip's real ReRAM address) while virt's
convention differs, and with -nographic and no UART wired up, a 5s timeout
with no crash is indistinguishable from "did nothing." Confirmed via
`-d guest_errors,unimp`: zero output logged. A guessed Baochip-shaped QEMU
machine (fake peripherals, fake memory map) was considered and rejected --
it would duplicate logic already correctly modeled in apple2_mem.c, has no
honest way to represent the BIO cluster (bio-sim already gives real RTL
behavior instead), and risks recreating the exact "trusted a plausible
artifact that didn't match reality" failure this project already hit twice
on documentation. Recommendation: do not build a guessed hardware target.

Framebuffer + 3-button host loop -- feasible, and mostly already built
---------------------------------------------------------------------------
Narrower ask (just a framebuffer + 3 buttons for host-side testing, not a
full peripheral simulator) is well-scoped and largely already exists in
this repo, verified directly:
- Framebuffer: bio_display_render_frame*() already produces real RGB565
  output; tools/fb_terminal_viewer.c already renders any RGB565 dump to
  the terminal via ANSI truecolor half-blocks (U+2580), no SDL2 needed.
  Confirmed working, reads a raw dump file and prints real pixels.
- Buttons: apple2_mem.c already maps $C061/$C062/$C063 to a 3-element
  pressed-state array; apple2_mem_set_button_state() is explicitly
  documented in its own header as "the test/host-side hook standing in for"
  real button GPIO. No new soft-switch plumbing needed.

Missing piece is glue only, not new architecture: a small interactive host
program (stdin key read -> apple2_mem_set_button_state() -> one
baoregon_emulator_run_frame() -> dump framebuffer -> fb_terminal_viewer_
print(), looped) would produce an actually-playable-in-terminal build using
only already-tested, already-real modules. This directly satisfies
NEXT_STEPS.md's own unchecked "host SDL2 or terminal viewer" item -- the
viewer tool's own header comment confirms this glue is "not yet done
anywhere in this codebase." Recommend bundling this with the disk-boot
integration test above (same missing piece: something that actually runs
the composed system end-to-end and lets a human watch it).
