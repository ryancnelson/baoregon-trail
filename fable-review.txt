===========================================================================
CRITICAL FINDING -- same failure class as the prior review, recurred
===========================================================================
Dashboard claim (dashboard.html, current): "Woz: 128 CPU Opcodes GREEN +
Klaus Dormann harness." This phrasing is actually more careful than last
time's false "100% passing" claim -- it only claims the harness EXISTS, not
that the suite passes. Good improvement in precision.

BUT: I ran tests/test_functional_suite.c directly (it builds fine, the
fixture tests/fixtures/6502_functional_test.bin is present) and it FAILS:

    FAIL: test_functional_suite_reaches_success_trap
    (trapped at $0FAB after 42450 steps -- expected success trap at $3469)

Root cause, confirmed by reading src/cpu6502.c directly: ADC/SBC do not
implement BCD (decimal mode) arithmetic. The code says so explicitly:

    case 0x69: { /* ADC immediate (binary mode only; decimal mode is a
                    separate future test per NEXT_STEPS.md flag coverage) */

This is a known, bounded, scoped-out gap -- not a mystery bug. But two
problems follow from it:

1. tests/test_functional_suite.c is NOT wired into `make test` (unlike
   test-firmware and test-biosim, which ARE documented as separate targets
   with an explicit comment explaining why they're excluded). This one has
   no such target and no such comment -- it's just silently absent. Anyone
   running `make test` and seeing "159 tests GREEN" has no way to know the
   actual ISA-correctness suite fails.
2. Decimal mode is used by real Apple II software more often than people
   expect -- BASIC's floating-point/string routines and various games'
   scorekeeping lean on it. This will surface as a real bug once actual
   Oregon Trail code runs, not just as an academic test-suite gap.

RECOMMENDATION (hardware in hand next week -- this is the highest-priority
open item): either (a) implement decimal-mode ADC/SBC now -- it's a
well-known, bounded algorithm, not exploratory work, or (b) if deferring,
add an explicit `make test-functional` target (mirroring the existing
test-firmware/test-biosim pattern) so the gap is visible and tracked in CI
language, not silently missing. Right now it is neither passing nor
tracked, which is the worst of both states.

===========================================================================
ARCHITECTURE / SECURITY -- holds up on direct inspection
===========================================================================
- Bus-abstraction contract (read6502/write6502 as the single seam for
  RAM/ROM/soft-switches) remains the right call -- it's what let three
  people's modules (Woz/Bunnie/Duke) develop in parallel against mocks and
  get swapped to the real bus later without cross-module coupling.
- Fast-sector-read disk trap (bypassing GCR/stepper emulation, direct ReRAM
  pointer copy) is a smart, correctly-scoped simplification given the
  actual goal (boot speed, not floppy-drive authenticity).
- Bounds-checking discipline is consistent everywhere I checked: rram_driver
  rejects unaligned/out-of-bounds writes (tested), disk_trap rejects
  invalid track/sector without corrupting state (tested), video decode has
  explicit first/last-column boundary tests (tested). This is real, not
  decorative.
- BRAINSTORM.md updates (Section 7 power numbers, BIO ISA confirmed as
  RV32IMC with reserved x16-x31 MMIO registers) read as incorporating real
  external information (Discord #c-side channel, bunnie huang directly)
  with appropriate epistemic hedging -- commit 9d00f76 explicitly labels
  claims "CONFIRMED-from-photo" vs "ASSUMED," which is the right posture
  for hardware not yet in hand.
- No meaningful new security-surface concerns beyond what was already
  noted last review (no external/untrusted input path reaches the decode
  functions; .dsk contents are baked in at build time, not loaded from an
  untrusted external source at boot).

===========================================================================
BOTTOM LINE
===========================================================================
Much stronger snapshot than the prior review, and the team fixed the exact
doc/reality mismatch pattern flagged before in most places (dashboard
language is more precise now, test-suite wiring is more complete). But the
identical failure mode reappeared once, in the highest-stakes possible
location: the CPU core's actual ISA correctness, one week before hardware
arrives. Fix the BCD gap or make its failure visible in `make test` before
anyone treats the 6502 core as done.
